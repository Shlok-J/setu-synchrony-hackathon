# Setu — Design Notes

Problem statement: "AI-Powered Financial Inclusion: Dynamic Risk Assessment for Underserved Segments" (Synchrony Hackathon, PS-II Sem II 2026-27).

## One-line thesis
Setu gives every underbanked applicant a real-time, explainable risk score from day one — a cohort-based estimate for brand-new users that automatically sharpens into a personalized score as their own transaction history grows — without ever using the social or demographic data that would make the score unfair or indefensible.

## 1. Data strategy
**Used** (each chosen for a defensible, explainable link to repayment capacity):
- Telecom: recharge frequency, amount, regularity, tenure on current number
- Utility/rent payment punctuality
- Digital transactions (UPI/wallet): frequency, average value, regularity, merchant diversity
- Platform tenure / KYC completeness

**Explicitly excluded:** social media / social-graph data, caste/religion/community indicators, granular location. Social-graph-based alt-data scoring is the single highest disparate-impact, least-auditable data category in this space — naming it and refusing it is a deliberate design choice, not an oversight.

## 2. The core mechanic — cohort score → personal score, blended
- **Cold start:** k-nearest-neighbor lookup, via a real pgvector similarity search (`model-service/model/db.py`) over an 8-dimensional PCA-learned embedding (`model/embeddings.py`) of the standardized features, against the cohort's historical repayment rate. Falls back to an in-process scikit-learn NearestNeighbors index automatically if Postgres is unreachable, so this can never break scoring.
- **Warm:** a gradient-boosting classifier trained on the applicant's own full feature vector.
- **Blend:** `score = (1 - w) * cohort_score + w * direct_model_score`, where `w = min(1, days_active / 90)`.
- This is the concrete answer to "dynamic/adaptive": the scoring *method* evolves per customer as trust is earned, not just periodic retraining of one static model.
- The risk score itself is never generated by an LLM — regulated credit decisions need auditable, simpler models. The LLM is used only downstream, to phrase an already-computed, already-audited result in plain English.

## 3. Fairness
The synthetic training data is generated so a single latent "financial discipline" factor drives both the alt-data features and the repayment outcome, with gender/region generated independently of it (`data/generate_synthetic_data.py`). `GET /fairness-report` runs the *trained model's own predictions* across the full population and reports approval-rate parity and a disparity ratio by gender and region (`model-service/model/fairness.py`) — checking the model's output, not just the raw label balance. On the current synthetic data this comes back at 0.89 (gender) and 0.96 (region), both clear of the standard 0.8 "four-fifths rule" threshold. The point of building this isn't "prove our synthetic data is fair" (that's cheap) — it's the audit *process* and tooling, which would run identically against real production data, where invisible feature correlations are the actual risk. Borderline scores routing to manual review rather than auto-decline (human-in-the-loop) is designed but not yet implemented.

## 4. Explainability
- Cold-start: "compared to N similar new customers, X% repaid on time."
- Warm: local feature attribution via permutation (perturb each feature to the population mean, measure the shift in predicted probability — the same family of idea as SHAP, chosen here to avoid an extra heavy dependency under time pressure; real SHAP is a natural production upgrade) → top factors → one LLM call turns them into a sentence.
- Guardrail: the LLM prompt may only rephrase the provided factors — no new claims, no demographic references (none are passed to it in the first place). See `model-service/model/explain.py`.

## 5. Privacy / compliance
- `POST /api/consent` must be called for an applicant before `/api/score` will run for them at all -- enforced server-side (403 if missing), not just a client-side checkbox. Maps to India's DPDP Act 2023: purpose limitation and consent before use.
- `DELETE /api/applicants/{id}` implements right-to-erasure as an actual endpoint, not just a policy statement -- wired into the UI as an "Erase my data" button.
- No hardcoded secrets; LLM/API keys read from environment variables only (see `.env.example`).
- Consent state and score history are persisted to real Postgres (`backend/.../service/ApplicantStore.java`, via `JdbcTemplate`, against the schema in `db/init.sql`) -- `score_history.result_json` stores the full score response as JSON text, which keeps `top_factors` intact without a fully normalized schema. `ApplicantStore`'s method signatures were designed from the start to mirror a real repository, so switching from the original in-memory placeholder to Postgres required zero changes to `ScoreController`.

## 6. Architecture
React (frontend) → Spring Boot (API/orchestration layer — owns auth, validation, and persistence) → Python model-service, FastAPI (owns the ML: pgvector-backed cohort lookup, gradient boosting, explanation generation) → Postgres+pgvector (applicant records, score history, and the cohort reference population's embeddings — schema in `db/init.sql`).

**Deployed live in the Codespace** (the AWS EC2 deployment at `http://43.204.147.211/` predates this change and has not yet been redeployed with it -- that instance's memory is tight enough that redeploying needs the other containers stopped first, per the notes on that incident). pgvector similarity search and the PCA embeddings model are now both real, verified via `/health`'s `pgvector_cohort_search` field and a direct count against `borrower_embeddings`.

Spring Boot calling out to a Python model-service is a deliberate, standard microservice split (Java for the service/API layer, Python for ML) — not a shortcut around using Spring Boot for real.
